# 0045 — Compose print with standalone asynchronous monitoring

- Status: accepted workflow direction; source validation and independent review pending
- Date: 2026-09-03
- Owners: project maintainers
- Milestone: F0 / I1 contract refinement; MON-001 and HANDOFF-002

## Context

A print request needs a clear transition from an observed start to continued
observation, while the primary agent remains available. Monitoring must also be
independently invocable for a job that was started elsewhere. The existing
u1-monitor-print skill already owns adaptive observation and terminal evidence;
it needs an explicit asynchronous owner and lifecycle, not a second monitor.

## Decision

Keep one standalone workflow in
[u1-monitor-print](../../plugins/u1-print-studio/skills/u1-monitor-print/SKILL.md).
"Monitor this print" invokes it directly. A broader "Print this" request composes
preparation, authorized upload/start, and this workflow after fresh evidence of
the exact job printing. Preparation-only, upload-only, and explicit start-only
requests keep their limited scope. Start acknowledgement remains an intermediate
update; it is not observed printing or a completed user outcome.

A delegated owner accepts a private target/run binding, known artifact and
manifest references, fresh complete telemetry, camera confidence and next check.
Use a print-session identity and start/progress evidence when available because
filenames can be reused. Unknown provenance stays unknown. One owner monitors one
bound run; duplicate requests reuse that owner. The primary receives meaningful
updates and immediate alerts and stays available for conversation. Unavailable
capacity is disclosed rather than described as active supervision.

The owner repeats complete evidence → identity comparison → assessment → adaptive
next due time → meaningful report → interruptible wait. Telemetry and camera
have independent timestamps and confidence. An outage is unknown/stale, with at
most three recovery attempts over three minutes before declaring monitoring
unavailable. A recovered or resumed owner rebinds from a fresh snapshot; a changed
run or uncertain identity never silently becomes the monitored job.

Verified complete, failed and cancelled print states are distinct from an
interrupted monitor or the user's "stop monitoring". The latter stops observation
and releases task-owned resources; it does not stop the printer. Paused printing
is not terminal. Completion keeps the existing fresh terminal-state, inactive
execution and end-of-print checks; layer N/N is insufficient. Visual concerns
remain advisory and require no automatic pause, cancel, resume or tuning.

Repository agents read the maintained source skill through AGENTS routing.
Installed plugin copies are not rewritten by this change. The workflow depends
on active conversation/worker execution; it does not install durable monitoring,
survive host closure, or add external notifications. Lost ownership is reported
as interruption, with a private handoff for explicit resumption.

## Boundaries and consequences

Preparation and operations remain peer subsystems. PREP-007's final-hash-bound
local thumbnail verification precedes upload; HANDOFF-007's target-parsed check
precedes start. Delegating monitoring does not expand printer authority, repair
an ambiguous start, retry a start, or alter an accepted artifact.

This is an F0/I1 workflow contract. It does not complete O1's persistent service
or O2's notification delivery. No MCP tool, application runtime, plugin manifest,
cache installation, service, network or authentication change is included.
The separate question of standardized one-shot observation tools is not decided
or implemented here. Source skill guidance can be followed in repository work
without claiming that installed plugin behavior or background delivery changed.

## Acceptance evidence

Validate the two changed skill folders and documentation contracts, verify all
application/dependency/configuration/generated bytes unchanged from the base,
and independently review the exact candidate. Exercise the instructions with
bounded fictional cases: standalone attachment, composed print, start-only,
duplicate monitor, paused job, repeated filename/new run, telemetry outage,
camera-only failure, terminal printing layer N/N, verified terminal outcome and
stop-monitoring. Such review is instruction/software evidence, not physical
printing, actual-host lifecycle or durable notification acceptance.

The active iteration's VALIDATION and HANDOFF record commands actually run,
identities, findings and remaining evidence boundaries. This documentation and
skill-only change needs no application deployment under decision 0028.
